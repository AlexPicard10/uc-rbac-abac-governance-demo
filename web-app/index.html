02RBAC · role-based access

Join a group, assume a role

Users join a member group that may ASSUME a role. Data is granted to roles only — member groups hold no access.

👤 generation_users
↓ assume
🔑 role_generation
✓ Generation
✕ Heating — denied
👤 heating_users
↓ assume
🔑 role_heating
✓ Heating
✕ Generation — denied
👤 cross_domain_users
↓ assume
🔑 role_cross_domain
✓ Generation FR rows only
✓ Heating FR rows only
ℹ️

Assuming a role replaces your base permissions with only that role's, for the session — one active role at a time. So even a workspace admin, acting as a role, is held to exactly what that role can see.

03ABAC · attribute-based access

One governed tag, one policy, both domains

A governed tag marks the country_code column so one catalog-scoped row filter covers both domains. Which rows each role sees comes from an entitlement table keyed on the assumed role: domain roles = all countries, the cross-domain role = FR + BE. Change access by editing a table row — no policy change.

✓ domain role · generation or heating
FR BE NL DE

All countries, within its one permitted domain.

🏷️ role_cross_domain · both domains
FR BE NL DE

Both domains — but the entitlement table limits this role to FR + BE.

A second ABAC policy — a column mask — redacts site_name → REDACTED for this role.

 01_governed_tag_abac.sql
-- entitlement table, keyed on the assumed role
INSERT INTO gov.role_country_entitlements VALUES
  ('role_generation',  'ALL'),
  ('role_heating',     'ALL'),
  ('role_cross_domain','FR'),
  ('role_cross_domain','BE');

CREATE FUNCTION gov.country_entitlement_filter(
    row_country STRING) RETURNS BOOLEAN
  RETURN EXISTS (SELECT 1
    FROM gov.role_country_entitlements e
    WHERE e.role_name = session_user()
      AND (e.country_code = 'ALL'
           OR e.country_code = row_country));

CREATE POLICY country_row_filter
  ON CATALOG governance_demo
  ROW FILTER gov.country_entitlement_filter
  TO `role_generation`, `role_heating`,
     `role_cross_domain`
  FOR TABLES
  MATCH COLUMNS has_tag('country') AS cc
  USING COLUMNS (cc);
⚠️

The filter compares session_user() — the active role. It must not use is_account_group_member('role_…'): a role is not a member of itself, so that is always false.

05Ontology · modeled + learned knowledge

KPIs defined once, trusted everywhere

The ontology is the context Genie searches to turn a question into the right SQL. We model it — certified metric views, rich comments, PK/FK relationships, a sites dimension — and the dashboard & queries add learned knowledge. The same certified measure answers in a dashboard and in Genie One.

 02_ontology_metrics.sql
-- define the KPI once, in YAML
CREATE VIEW generation.generation_metrics
  WITH METRICS LANGUAGE YAML AS $$
  measures:
    - name: Capacity Factor Pct
      expr: 100 * SUM(generation_mwh)
            / SUM(dim_asset.capacity_mw * 24)
  $$;
-- mark it trusted for Genie
ALTER VIEW generation.generation_metrics SET TAGS
  ('system.certification_status'='certified');

-- one measure, reused everywhere
SELECT `Asset Type`,
  MEASURE(`Capacity Factor Pct`)
FROM generation.generation_metrics
GROUP BY `Asset Type`;  -- wind ~55% · solar ~19%
✨

An AI/BI dashboard and Genie One read the same certified measure — and the published dashboard feeds its queries back as learned knowledge. Because the metric views sit on the governed base tables, the KPIs stay governed: the dashboard is published with individual data permission, so each viewer runs it with their own UC permissions and the cross-domain role's numbers cover FR + BE only — the same governance in the dashboard as in Genie One.
